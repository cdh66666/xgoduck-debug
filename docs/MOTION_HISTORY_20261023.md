# 动作历史与静止无线排查

用户报告“点击站立后仍后倒”，此前17～19秒只是有限试验窗口，站立稳定性仍未通过。用户随后将鸭子放回托盘并禁止舵机动作；当前板端保留`data/motion-inhibit`，动作API在调用控制器前拒绝上力、姿态/校准和维护移动，仅允许读取与卸力。此锁需要新的明确运动授权才解除，不随重连或服务重启自动撤销。

## 已落地

- 鸭子端25Hz被动状态快照；已接受模式切换额外即时留事件，避免短请求落在周期采样之间。包含15轴编码器/记录期望角、Host策略目标、指令、滤波重力、原始IMU、模型阶段、错误、零位快照、源时钟和源码/ONNX哈希。它不是50Hz全部ONNX观测/动作或原始DOM点击记录。
- 每段含约1秒前后数据，独立线程压缩保存；长动作按5分钟分段，板端16MiB滚动缓存。电脑通过GET同步到`pc/motion-recordings/`长期保存。浏览器关闭或无线暂断不停止板端采样；板端滚动缓存并非无限离线存储。
- 实时姿态右侧选择历史，真实16网格模型用实测角度回放，支持¼倍/½倍/1倍/2倍、逐帧、拖动、倾角时间轴及原始gzip下载。回放路径没有动作请求，动作中先卸力才能切换；当前托盘锁始终保留停止/卸力。
- 已导入5条此前完整实机状态抓取和2条最近原始反馈片段。两段旧原始包为1268/952帧，MCU上力跨度约10.67/7.51秒；具体点击仅按时间关联。原始acc/gyro/编码器保留，缺失的滤波gravity、模型阶段、输入和终止原因不补造。可选机身估算放在`body_attitude_estimate`，橙色虚线标明估算，不生成自动站起/后倒定位。`targets`为记录期望角，不是经过raw范围裁剪后的最终总线目标。

## 无线显示修复

旧播放器把电脑收包时间当成动作时间。源端等间隔产生的姿态经Wi-Fi成批到达，会被压缩成快速动作，之后又停住；接收空档也会被误认作源端缺帧。当前按鸭子端`uptime_s`安排真实端点，使用0.35秒画面缓冲；模型、15轴、读数和曲线保持同一时轴，不外推或改变真实缺帧的300ms边界。当前接收年龄、启动资格、命令看门狗和板端传感保护仍独立判断。

对两段各20秒的真实静止接收轨迹，以相同40Hz时钟、排除首秒和末端无后续数据的口径回放：旧100ms播放器冻结帧占13.76%/11.71%，新“源时钟＋350ms缓冲”组合均为0。仅改时钟而不补足缓冲不能得到该结果；这证明这两段轨迹的显示改善，不是无线根因已修复或所有链路都零冻结。真实缺帧/缓冲耗尽时徽标优先显示保留姿态，即使接收通道刚恢复也不把旧画面称作当前姿态。

板端记录与HTTP状态流共用一次采样，避免新增记录器与每个网页订阅者重复取完整状态。缓存年龄计入反馈、关节、航向、电流和电压的新鲜度；源uptime/序号保持原值，缓存不能续期成新数据。

静止抓取还出现过Linux uptime继续前进而MCU帧号回退的源端重同步迹象。当前状态明确携带接收世代、MCU启动时钟标记和源采样时间；已确认接收世代变化时，电脑另起显示世代，不再等旧MCU序号追平。Linux网络积压参考保持原样，不把重同步当成清除网络延迟的理由，也不改变控制器的保守卸力/重新静止资格规则。该旧抓取缺完整世代字段，不能据此判定真实MCU重启或锁定后倒原因。

## 追加：积压新鲜度修正与逐行写出审计

旧电脑端只在板端报告年龄上增加电脑接收后的缓存时间，漏掉了已经能从源时钟判断的相对积压。复用原有763行静止接收记录，97行（去重95个端点）在积压超过150ms时仍报告ready；例如observation 13516报告7.26ms，但相对积压已有331.47ms。修补同时更新当前反馈/各轴年龄、ready和stale字段，浏览器响应排队也继续携带这部分年龄；原始历史端点的反馈年龄、资格、姿态、角度、时钟和序号不改。

设N为收到的板端反馈年龄（已含板端缓存C），B为现有10秒源时钟参考得到的相对积压，P为电脑接收后缓存时间。当前副本采用`N + max(0, B-C) + P`，避免重复计算C。旧包没有C时采用保守的`max(N,B)+P`。这个计算沿用源时钟连续且短窗速率差可忽略的假设；它不能测出恒定延迟基线，年龄小于150ms不证明绝对端到端新鲜。来源有效但传输迟到的真实端点仍进入画面缓冲，来源年龄达到150ms的端点仍拒绝，当前资格和历史画面分别标注。

已读取板端实际安装的Starlette 0.48.0、Uvicorn 0.38.0和Arduino WebUI 0.5.0相关源码：StreamingResponse每块交给ASGI，httptools路径逐块调用transport.write；64KiB是写积压的反压门槛，不是攒满后才发送的阈值。本机实际HTTPResponse.readline离线对照中，完整NDJSON行可在HTTP chunk尾或同chunk后续内容到达前返回（约0.26～0.30ms）；故意扣住换行300ms则会等约310ms。正常20Hz十帧均读出，最大JSON解析约0.13ms。未发现应用主动攒批的代码，但transport.write也不等于已经送达电脑。

当前30秒原始记录中，最大相邻到达空档378.92ms对应源快照前进33.98ms、序列化前send stamp前进52.06ms，二者间多出326.86ms等待；整段最大send stamp间隔83.75ms。此stamp位于JSON编码和socket写出之前，接收stamp位于完整行读取之后，现有记录不能再区分传输缓冲、系统/SSH队列、无线传输和接收行尾等待。准备的板端隔离ASGI夹具未执行：两次SSH分别在banner交换超时、由对端关闭，不能记为测试通过，也没有修改任何无线参数。

本次追加验证为5项年龄测试、20项本机HTTP状态流测试、15项Node姿态/控制测试及270项已有UI行为检查，均通过；未新增实机采样或动作。修补源码版本为`2026-10-23-motion-history-r2`。收尾单次GET返回无线未连接，正在运行的电脑服务仍为r1；因无法取得新的OFF/disabled确认，未重载该服务或鸭子控制器。静态资源文件已更新，电脑后端的本次年龄修正仍待安全重载，不标为已实机生效。
