# 2026-10-24 板端 50 Hz 周期与地面实测

## 已修复的根因

控制线程过去一次略超 20 ms 就跳过下一槽位，诊断统计又在控制共享锁内排序、复制，HTTP 状态序列化进一步争用 Python 执行时间。因此传感反馈接近 100 Hz 时，模型仍可能只有 37–43 Hz。

现在保留 20 ms 时钟相位，小幅超时立即进入下一步；落后超过整周期才重定基准，不补发积压动作。状态统计移出控制锁，HTTP 使用已有 25 Hz 记录快照并更新数据年龄，快照复制改用内存中的内置类型序列化，缩短 GIL 调度片。安全准入和实际控制仍读新反馈。

运动指令接口只校验、写入最新意图槽并返回 HTTP 202 / accepted_seq；控制线程在下一周期取走最新值。旧值被覆盖，不排队，不等电脑下一条命令才运行策略。四个模型在启动阶段加载、预热。消费回执包含 sequence / wait_ms / applied；策略记录再关联 control_intent_seq 和发送序号。applied 仅表示板端消费了目标，实机是否使能、MCU 是否收到须分别看反馈。OFF 即时卸力，并使正在推理的旧输出失效。

这一周期接口用于实时运动意图。模型文件加载、校准写盘、改编号等维护操作仍不是 20 ms 实时接口，也不应塞入运动周期。

## 实测对比

同一设备、相同权重、卸力 shadow 模式，用本地控制线程实际推理次数测频率；以下是短窗数据，前后时长不同，不代表长期或最坏情况保证。

| 条件 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 不轮询状态 | 43.06 Hz / 3.16 s | 49.96 Hz / 6.04 s |
| 持续轮询状态 | 37.01 Hz / 3.35 s | 49.80 Hz / 6.16 s |

最终单槽接口另测 6 秒，189 次请求、138 个采样到的消费回执，29 个旧意图被覆盖，0 个请求错误，全程观测到电机未使能：

- 模型推理 50.005 Hz；开始间隔平均 20.002 ms、P99 29.879 ms、最大 32.581 ms。
- 板端收件到周期消费平均 7.941 ms、P99 19.713 ms、最大 20.485 ms。
- HTTP 往返平均 29.584 ms、P99 72.404 ms。网络往返与板内消费等待是不同指标。

没有增加显示缓冲。Linux/Python 调度仍有长尾，不能把平均 50 Hz 表述为每周期绝对不超过 20 ms。原始数据在本机 `pc/qa/ground-20261024/`：`shadow-timing.json`、`shadow-timing-gil.json`、`mailbox-native.json`。

## 实机仍未通过站立验收

用户已明确放到空地并授权测试。首轮起身后摔倒；修复控制时钟后，再做零行走指令的有界测试，约 2.15 s 再次倒下，保护恢复 OFF、enabled=false、motion_inhibited=true。

后一次记录包含 102 个推理开始间隔，平均 19.992 ms、P99 31.798 ms、最大 36.491 ms。约 1.03–1.38 s 倾角低于 15°，最长起身确认累计 0.44 s，未达到现有 1 s 交接条件；整个观测都在 getup，未切到 walk。直立片段仍有较大角速度和冲击，单凭倾角不能认定支撑已稳。测试电压约 7.8→7.6 V；此前一轮的 5.7 V 出现在跌倒后，不能作为首次失稳的原因。

这证明控制频率问题已改善，但没有证明起身稳定性已修复。未盲目缩短交接阈值，未改变模型、机械零位或舵机参数。后续需区分起身动作、稳定支撑与 Walk 交接。真实记录：`zero-stand-first.json`、`zero-stand-50hz-mailbox.json`，以及动作历史中的同期记录。
